# Beeper Audio — 1-Bit Sound on the ZX Spectrum

The ZX Spectrum has no sound chip. One speaker. One bit. All audio is generated by the CPU toggling a single output line fast enough to vibrate the cone.

This explainer covers how that works, how 1-bit music engines fake polyphony, and how it maps to Web Audio API concepts.

---

## How the Beeper Works

The speaker is wired to **bit 4 of I/O port 0xFE**.

```z80
OUT (0xFE), A    ; write A to port 0xFE — bit 4 drives the speaker
```

- Bit 4 = 1 → cone pushed out
- Bit 4 = 0 → cone pulled back

That's it. No DAC. No volume register. No sound chip. The CPU toggles the bit on and off, and the speaker cone follows.

The Spectrum runs at **3.5 MHz** (3,500,000 T-states per second). Every OUT instruction costs T-states, so timing is measured in CPU cycles.

---

## Generating a Tone — Frequency from Cycle Counting

A square wave is just the speaker alternating between high and low at a fixed rate.

```
freq = 3,500,000 / (2 × half_period_tstates)
```

- `half_period_tstates` = how long you hold each state before toggling

**Example — middle C (261.6 Hz):**

```
half_period = 3,500,000 / (2 × 261.6) ≈ 6,693 T-states
```

The basic tone loop in Z80 assembly:

```z80
; Play a tone for a fixed number of half-periods
; B = delay count (controls frequency)
; D = half-period repeat count

tone_loop:
    LD B, delay        ; load delay value
wait:
    DJNZ wait          ; burn T-states (DJNZ = 13 T-states when looping)
    LD A, 0x10         ; bit 4 high
    XOR speaker_state  ; toggle
    OUT (0xFE), A      ; send to speaker
    DEC D
    JR NZ, tone_loop
    RET
```

DJNZ (Decrement B and Jump if Not Zero) is the key instruction — it's the Spectrum programmer's precision timer. Each iteration burns a known number of T-states, so you can dial in a specific frequency by choosing `delay`.

You derive the delay from the formula above, subtract the fixed overhead of the loop instructions themselves (the OUT, XOR, DJNZ, etc. all cost T-states), and what's left goes into the DJNZ counter.

## 1-Bit Music Engines — Faking Polyphony

A single bit can only be on or off. Real music has multiple simultaneous notes. How do Spectrum games and demos produce rich-sounding chords and melodies?

**The core trick: interleaving channels within a single frame.**

Within one display frame (~20ms / 50Hz), the engine rapidly switches between playing different frequencies. If the switching is fast enough, the ear hears multiple pitches simultaneously.

```
Frame (20ms):
  [chA half-period] [chB half-period] [chA half-period] [chB half-period] ...
```

Each "channel" gets a slice of the frame. The CPU must finish all the half-periods for all channels before the next frame interrupt.

### Common Engines

| Engine | Technique | Channels |
|--------|-----------|----------|
| **Phaser** | Two tones interleaved; phase difference creates beating and chords | 2 |
| **Tritone** | Three interleaved frequencies; strict timing budget per frame | 3 |
| **Music Box** | Percussive attack + pitch decay; melody + drums + bass | 3 |
| **QChan** | Five-channel engine with pitch tables; used in late-era demos | 5 |

### Timbre from Duty Cycle

The beeper is on or off — but *how long* it spends on vs off within each cycle changes the sound quality.

- **50% duty cycle** → pure square wave, bright and buzzy
- **Short pulses** → thinner, quieter (less energy)
- **Asymmetric duty** → different timbres — used to fake bass vs treble

This is **pulse width modulation (PWM)** on 1 bit. By varying the ratio of on-time to off-time, the engine shapes the perceived timbre — all without a DAC.

### Beepola

[Beepola](https://shiru.untergrund.net/beepola.shtml) is the primary tracker for composing Spectrum beeper music. It exports Z80 routines using any of the above engines. You write notes; it handles the timing arithmetic.

## Web Audio API Comparison

The same audio concepts appear at both ends of the technology spectrum — they're just implemented differently.

| Concept | ZX Spectrum | Web Audio API |
|---------|------------|---------------|
| Sound generation | CPU toggle loop | `OscillatorNode` |
| Volume control | Not available | `GainNode` |
| Timing | T-states, DJNZ loops | `AudioContext.currentTime` |
| Multiple channels | Interleaved illusion | Real parallel nodes |
| Output | 1-bit DAC (the speaker cone) | Float32 sample buffers |

### ADSR Envelopes

Web Audio has proper ADSR (Attack, Decay, Sustain, Release) via `gainNode.gain.setValueAtTime()`.

The beeper approximates this:
- **Attack** → rapid series of short pulses that grow in duty cycle
- **Decay** → opposite — pulses shorten after the initial hit
- **Sustain** → constant frequency tone
- **Release** → no hardware support; the engine just stops

It's faked with timing tricks, not actual volume control.

### Sample Rates

Both systems use sample rates — they just differ in scale.

- Web Audio: 44.1 kHz or 48 kHz sample rate, floating-point buffers
- Spectrum: effectively ~3.5 MHz "sample rate" (every T-state is a potential output change), but practically limited to a few kHz for audible tones

## Coming from JS/TS

If you've used Web Audio API, here's how the concepts map:

```ts
// Web Audio
const ctx = new AudioContext();
const osc = ctx.createOscillator();
osc.frequency.value = 440;  // Hz

const gain = ctx.createGain();
gain.gain.value = 0.5;      // half volume

osc.connect(gain).connect(ctx.destination);
osc.start();
```

```z80
; ZX Spectrum equivalent

; "new AudioContext()" → the beeper is always ready
;   just write to port 0xFE

; "osc.frequency.value = 440" → calculate T-state delay:
;   half_period = 3,500,000 / (2 × 440) = 3977 T-states
;   subtract loop overhead, load remainder into B

; "gain.gain.value = 0.5" → not possible
;   beeper is binary — on or off

; "osc2.frequency.value = 880" → second "oscillator"
;   is just the same loop interleaved within the frame
```

Key differences:
- **No volume** — you simulate it with duty cycle and pulse density
- **No parallel threads** — all "channels" share one CPU executing sequentially
- **Timing is absolute** — every instruction has a fixed T-state cost; there's no async scheduler

## In Practice — Business Parallels

The beeper engine is a master class in resource-constrained systems:

- **Embedded / IoT audio** — piezo buzzers and single-bit outputs on microcontrollers use the same technique. PWM audio on an Arduino is the same problem.

- **Resource-constrained playback** — mobile, edge, and wearable devices often have strict CPU budgets for audio. The interleaving trick maps directly to prioritising audio tasks within a fixed time window.

- **Audio codec design** — the beeper forces you to think about the minimum information needed to represent sound. 1-bit audio at the extremes is the conceptual opposite of lossless PCM, but both are about what you can discard.

- **Real-time scheduling** — a multi-channel beeper engine *is* a real-time scheduler. Each channel has a deadline (its half-period), and the CPU must service all of them within the frame. Miss a deadline → audible glitch. This is the same problem as hard real-time embedded systems.

- **Perceptual tricks over fidelity** — the goal isn't accuracy, it's fooling the ear. This maps to perceptual audio codecs (MP3, AAC) which discard information the ear won't notice.

## Key Numbers to Remember

| Value | Meaning |
|-------|---------|
| 3,500,000 | T-states per second (Spectrum clock) |
| 69,888 | T-states per frame (50 Hz) |
| ~6,693 | Half-period T-states for middle C (261.6 Hz) |
| 13 | T-states per DJNZ loop iteration |
| 11 | T-states for OUT (0xFE), A |
| 4 | Bit position of speaker in port 0xFE |

The formula you'll use most:

```
half_period_tstates = 3,500,000 / (2 × target_freq_hz)
delay_loops = (half_period_tstates - fixed_overhead) / 13
```

Where `fixed_overhead` is the T-state cost of everything in the loop except DJNZ (OUT + XOR + any bookkeeping).

# A11Y.md — Web game accessibility research

Research notes for making WASM game content accessible, with focus on vision impairment.

## Why web games have an a11y opportunity

Canvas is opaque to assistive tech — screen readers see nothing. But the web platform gives us tools that native games don't have:

- **DOM overlay** — hidden HTML alongside the canvas gives screen readers something to traverse
- **Web Audio spatial API** — `PannerNode` + HRTF for positional audio, free in all browsers
- **Web Speech API** — `speechSynthesis.speak()` for self-voicing without external screen reader
- **CSS media queries** — `prefers-reduced-motion`, `prefers-contrast` detect user preferences
- **No install barrier** — important for users on locked-down or assistive-tech-configured systems

Keyboard-only input (which we already have) is a strength — it's how most blind gamers play.

## How blind/low-vision players play games

Three layers of audio replace visual information:

### 1. Dialogue / narration

Describes what's happening. Reads menus, announces state changes, narrates scene transitions. Game-specific narration is better than relying on a generic screen reader — the game knows what matters.

### 2. Sound effects (SFX)

Each game object/event gets a distinct, recognisable sound. "Enemy approaching", "health low", "wall ahead" — all communicated through unique audio cues. The key design principle is **distinctness**: every important game element must sound different from every other.

### 3. Spatial / ambient audio

Stereo panning or binaural audio communicates *where* things are. A tone shifts left/right as enemies move. Footsteps get louder as something approaches. Web Audio's `PannerNode` with HRTF (Head-Related Transfer Function) simulates 3D positioning through headphones.

Source: [Máté Moldován — Game audio accessibility](https://medium.com/@mateemoldovan)

## Guidelines framework

[gameaccessibilityguidelines.com](https://gameaccessibilityguidelines.com) organises guidelines by category (Motor, Cognitive, Vision, Hearing, Speech, General) and difficulty (Basic, Intermediate, Advanced).

### Vision — relevant to us

**Basic:**
- High contrast between text/UI and background
- Don't convey essential info by colour alone
- Large, well-spaced interactive elements (especially touch screens)
- Simple, clear text formatting
- Readable default font size

**Intermediate:**
- Screen reader support (including mobile)
- Distinct sounds per game object/event
- Spatial/surround audio
- Separate volume controls (effects vs speech vs music)
- Option to adjust contrast
- Option to hide background movement
- Allow interfaces to be resized

**Advanced:**
- Audio description track
- Binaural audio simulation for headphones
- Self-voicing (game reads its own UI without external screen reader)

### General — relevant to us

- Allow settings to be saved/loaded
- Provide training/practice level
- Allow game speed adjustment
- Ensure all areas can be navigated by keyboard alone

Source: [Game Accessibility Guidelines — full list](https://gameaccessibilityguidelines.com/full-list/)

## Recommended workflow

From [blindgaming.no](https://blindgaming.no/resources/):

1. **Guidelines** — read the relevant guidelines for your game type
2. **Plan** — decide which guidelines to target before building
3. **Implement** — build the features
4. **Test** — with actual assistive tech (screen readers, not just keyboard-only)
5. **Describe** — document what accessibility features exist (and don't). Even partial a11y is useful if players know what to expect.

## Mirror DOM pattern (from toolkit/flare)

We have a working implementation of this in `src/b/toolkit/flare/`:

- **`mirror-dom-core`** (Rust) — `SemNode` struct with `Role` enum (Region, Image, Table, Cell, Live, etc.) and `Describable` trait. Game state implements `Describable` → produces a tree of semantic nodes.
- **`mirror-dom.js`** (JS) — `buildMirrorDom()` takes the semantic tree, creates hidden HTML divs positioned at pixel coordinates. Screen-reader-only data tables for structured content. `announce()` pushes text to an `aria-live` region.
- **`chart/animation.rs`** — `prefers_reduced_motion()` checks the CSS media query from WASM and disables animation accordingly.
- **`chart/text.rs`** — respects WCAG 1.4.12 text spacing (letter-spacing, word-spacing).

The pattern: game state → `Describable` → `SemNode` tree → JS mirror DOM → screen reader access + focus rings.

## How this maps to our WASM player

We control both the content pipeline and the player, which is unusual — most games only control one.

### `type()` bitmask extension

Current: bit 0=image, bit 1=audio, bit 2=keyboard.

Possible: bit 3=a11y metadata. A data segment with scene descriptions, object positions, labels. The player reads it and builds the mirror DOM automatically.

### Sonification

Our beeper engine already generates audio from data — the same principle serves a11y. Game state → audio cues. We're building the primitives for this in the audio pipeline.

### Self-voicing

`speechSynthesis.speak()` is zero-dependency. The player could announce:
- Scene descriptions on load
- State changes during gameplay
- Menu options on focus

### `prefers-reduced-motion`

Already implemented in toolkit/flare. The WASM player should respect this — disable animation, reduce motion, provide static alternatives.

### `prefers-contrast`

High-contrast mode could switch palette or increase border visibility. Detectable via `matchMedia('(prefers-contrast: more)')`.

# Sigil Design

A sigil is a YAML spec describing one function. It's the input to the entire incant pipeline — RAG retrieval, LLM prompting, assembly, and testing all flow from what's in the sigil.

## Anatomy of a sigil

```yaml
name: add                        # unique identifier
description: Add two 32-bit integers.  # what the LLM should build
target: wat                      # output format: "wat" or "z80"

signature:
  inputs:
    - name: a
      type: i32
    - name: b
      type: i32
  output:
    type: i32

export: add                      # WAT only: wasm export name

tests:
  - inputs: { a: 2, b: 3 }
    expect: 5
  - inputs: { a: -1, b: 1 }
    expect: 0
```

Every field has a specific consumer in the pipeline:

| Field | Used by | Purpose |
|-------|---------|---------|
| `name` | gen.py, stitch.py | Unique ID, output filename, dedup key during stitching |
| `description` | gen.py | Injected into the LLM prompt — this is how the LLM knows what to build |
| `target` | gen.py, gate | Selects which backend (WAT or Z80) to use |
| `signature` | gen.py, gate | Types and names go into the prompt; gate uses them to set up test inputs |
| `export` | gen.py (WAT) | Tells the LLM to export this function from the WASM module |
| `memory` | gen.py (WAT) | Declares memory pages the function needs |
| `tests` | gate | Input/output pairs the gate checks after assembly |
| `dependencies` | manifest.py, gen.py | Other sigils this one calls — used for topological sort and context injection |

## Z80 vs WAT differences

Z80 sigils use registers instead of abstract types:

```yaml
name: add
target: z80
signature:
  inputs:
    - name: a
      register: A        # map to CPU register
      type: u8
    - name: b
      register: B
      type: u8
  output:
    register: A           # result register
    type: u8
tests:
  - inputs: { a: 2, b: 3 }
    expect: { a: 5 }      # expect is a register map, not a scalar
```

Key differences:
- **Registers** — Z80 inputs/outputs map to specific CPU registers (A, B, C, etc.). WAT uses stack-based parameters.
- **Test expectations** — Z80 expects a dict of register values (`{ a: 5 }`). WAT expects a single return value (`5`).
- **Export** — WAT sigils declare an `export` name. Z80 has no equivalent (code runs from address 0).
- **Memory** — WAT can declare `memory: 1` for pages of linear memory. Z80 has a fixed 64K address space.

## Dependencies

A sigil can declare that it calls functions from other sigils:

```yaml
name: sum_of_factorials
dependencies:
  - factorial
  - add
```

During multi-sigil builds, the pipeline:
1. Topologically sorts sigils so dependencies are generated first
2. Injects the generated code of dependencies into the LLM prompt
3. The LLM sees real function signatures and can `call` them

This means `sum_of_factorials` doesn't need to re-implement `factorial` — it calls the version already generated by the pipeline.

> **Coming from JS/TS:** Think of dependencies like ES module imports — declaring what you need, resolved at build time. The difference is there's no `import` statement in the generated code; the functions are stitched into the same module.

> **Coming from C:** Like forward-declaring functions that will be linked later. The LLM gets the actual implementation as context (like having the `.c` file available), but the final binary has them merged into one translation unit.

## Design principles

**One function per sigil.** Composition happens at the manifest level, not inside individual sigils. This keeps each spec focused and testable in isolation.

**Tests are mandatory.** The gate won't pass code that doesn't have tests. Tests are the quality gate — if it assembles and all tests pass, it ships.

**Description is the prompt.** The `description` field is the primary instruction to the LLM. A vague description produces vague code. Good sigils have specific, unambiguous descriptions.

**Types are constraints.** The signature types (`i32`, `u8`, `f32`) constrain what the LLM generates and how the gate sets up test inputs. They map directly to the target's type system.

> **In practice:** This one-spec-per-function pattern maps to any system where you want verifiable code generation. API endpoint specs, database migration specs, compliance-checkable output — anywhere "compiles and passes tests" is a stronger guarantee than "looks right to a reviewer."

## File naming

```
sigils/
  examples/          — single-function sigils for testing
    wat_add.sigil.yaml
    z80_counter.sigil.yaml
  programs/          — multi-sigil manifests
    wat_math.manifest.yaml
    wat_composed.manifest.yaml
```

Convention: `{target}_{name}.sigil.yaml` for sigils, `{target}_{name}.manifest.yaml` for manifests.

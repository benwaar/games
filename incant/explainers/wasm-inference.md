# WASM Inference Engine — Deterministic WAT from ONNX Weights

How incant turns a trained ONNX model into a self-contained WASM binary with no LLM, no runtime, and no dependencies — just the weights baked into the binary.

## Why WASM?

The Z80 target (`z80_infer.py`) runs inference on emulated hardware — useful for studying integer arithmetic constraints but not deployable. WASM is the opposite: it runs natively in every modern browser and Node.js, at near-native speed, with full float32 precision. The same ONNX model that runs as Z80 INT8 assembly can also run as a WASM f32 module — and both are generated by the same pipeline.

## The pipeline

```
ONNX model
    ↓  parse_onnx()           extract layer shapes, f32 weights, f32 biases
    ↓  generate_wat_inference()  emit WAT source: data segments + helper funcs + infer()
    ↓  wat2wasm               assemble to .wasm binary
    ↓  node wasm_infer_runner.js  (tests) write input → call infer() → argmax
```

No LLM. No quantisation. The WAT is computed directly from the weights — this is a compiler, not a generator.

> **Coming from C:** This is like writing a C compiler that outputs assembly. The "source language" is the ONNX graph; the "target language" is WAT. The output is deterministic given the same input.

> **In practice:** Production ML deployment tools like ONNX Runtime do exactly this — compile a model graph to an optimised binary. This is a minimal, readable version of that idea.

## Memory layout

WASM uses a single flat linear memory (like C's heap). All buffers and weight data live at fixed offsets. For a network with `in_dim` inputs, `hid_dim` hidden neurons, `out_dim` outputs:

```
offset               0: input buffer    in_dim  × 4 bytes (f32)
offset        in_dim*4: hidden buffer   hid_dim × 4 bytes (f32)
offset  (in+hid_dim)*4: output buffer   out_dim × 4 bytes (f32)
   ↓ data segments (weights baked in at build time) ↓
offset         out_end: fc1 weights     in_dim  × hid_dim × 4 bytes
offset          w1_end: fc1 bias        hid_dim × 4 bytes
offset          b1_end: fc2 weights     hid_dim × out_dim × 4 bytes
offset          w2_end: fc2 bias        out_dim × 4 bytes
```

The caller writes f32 input values at offset 0, calls `infer(0)`, and reads back the argmax class index (i32).

For TinyNN (80→32→95), total data is ~23.7 KB — well within one WASM page (64 KB).

### Why fixed offsets?

WASM has no malloc. The memory layout is computed at code-gen time and hard-coded into every `i32.const` address in the WAT. This is the same as a linker deciding where to place each symbol in a binary.

> **Coming from JS/TS:** Think of it as a static object layout, like a C struct with a known field offset for each member. There's no garbage collector moving things around.

## WAT data segments

Weights are emitted as `(data ...)` declarations — raw bytes copied into linear memory when the module is instantiated:

```wat
(data (i32.const 36) "\51\51\7e\3e\28\95\8d\bd...")
;;                    ↑ offset      ↑ f32 LE bytes, one per weight
```

The bytes are produced by `struct.pack('<' + 'f' * n, *weights_flat)` — little-endian IEEE 754 f32. Each `\xx` is one hex-escaped byte.

```python
def _f32_to_wat_string(values: list[float]) -> str:
    raw = struct.pack("<" + "f" * len(values), *values)
    return "".join(f"\\{b:02x}" for b in raw)
```

> **Coming from C:** This is the `.rodata` section of an ELF binary — constant data baked into the binary at a known address.

## The `$fc` function

The core computation is a dense (fully-connected) layer. For each output neuron `j`:

```
out[j] = bias[j] + Σ_i( in[i] * weight[j][i] )
```

In WAT, this is two nested loops using `f32.load`, `f32.mul`, `f32.add`, `f32.store`:

```wat
(func $fc
      (param $in_ptr i32) (param $out_ptr i32)
      (param $w_ptr  i32) (param $b_ptr  i32)
      (param $in_dim i32) (param $out_dim i32)
  ...
  ;; outer loop: j from 0 to out_dim
  ;;   acc = bias[j]
  ;;   w_row = w_ptr + j * in_dim * 4
  ;;   inner loop: i from 0 to in_dim
  ;;     acc += in[i] * w[j * in_dim + i]
  ;;   out[j] = acc
  ...
)
```

The function is generic — it takes all dimensions as parameters. The same `$fc` handles both layers; the `infer` function calls it twice with different pointers and dimensions.

> **Coming from C:** This is exactly what `cblas_sgemv` does, just written by hand in assembler. The inner loop is a dot product; the outer loop iterates over output neurons.

## ReLU and argmax

Two short helper functions:

**`$relu_buf`** — applies `f32.max 0.0` in-place to a buffer. Called between layers to zero out negative activations.

**`$argmax`** — scans the output buffer and returns the index of the largest f32. This is the predicted class. Returns an `i32`.

```wat
(func $argmax (param $ptr i32) (param $len i32) (result i32)
  ;; track best_val (f32) and best_idx (i32)
  ;; scan from index 1: if val > best_val, update both

)
```

## The exported `infer` function

The entry point the host (browser or test runner) calls:

```wat
(func (export "infer") (param $in_ptr i32) (result i32)
  (call $fc   ...)   ;; layer 1: input → hidden
  (call $relu_buf ...)  ;; ReLU on hidden buffer
  (call $fc   ...)   ;; layer 2: hidden → output
  (call $argmax ...)    ;; return argmax of output
)
```

The memory is also exported (`(memory (export "memory") 1)`) so the host can write inputs directly:

```js
// In JavaScript
const mem = new DataView(instance.exports.memory.buffer);
floats.forEach((v, i) => mem.setFloat32(i * 4, v, true));  // little-endian
const classIdx = instance.exports.infer(0);
```

## Testing strategy

The test (`tests/test_wasm_infer.py`) checks two things:

1. **Assembly gate** — `wat2wasm` accepts the generated WAT without error
2. **Accuracy** — 100 random inputs, argmax agreement ≥ 95% vs `onnxruntime`

Because the WASM uses full f32 (same as onnxruntime), agreement is typically 100%. The 95% threshold exists as a safety margin for numerical edge cases (NaN, ties).

The Node.js shim (`tests/wasm_infer_runner.js`) handles the test execution: it writes hex-encoded f32 bytes to WASM memory and calls `infer(0)`. This avoids adding a Python WASM runtime as a dependency.

> **Coming from JS/TS:** The test is the same pattern as testing a compiled Rust WASM module — you instantiate it, poke the memory, call the export, check the result.

## Comparing Z80 and WASM backends

| | Z80 (`z80_infer.py`) | WASM (`wasm_infer.py`) |
|---|---|---|
| Precision | INT8 (quantised) | f32 (full) |
| Weight encoding | `db` bytes (signed) | f32 LE data segments |
| Memory model | Fixed Z80 addresses | Linear WASM memory |
| Activation | Byte-clamp after shift | `f32.max 0.0` |
| Argmax | Signed byte comparison | f32 `f32.gt` comparison |
| Host | Z80 emulator (Python) | Browser / Node.js |
| Speed | ~6s at 3.5 MHz (emulated) | µs (native JIT) |

Both are deterministic — given the same weights, they produce identical WAT/ASM every time.
